# 记忆设计草案

目标：支持多年陪伴与往事回顾；随着聊天历史增长，控制每轮发送的上下文体积，并让用户能够知道系统记住了什么、依据是什么、如何修正或忘记。

状态：原始聊天长期保留、低重要性先淡细节以及判断随交流调整已确认。部分机制已在本机验证版实现，真实模型效果和后续机制见 [运行文档](running.md)。

## 重要性、完整性与个体偏好

每条记忆分别保存事件轮廓、已知细节、重要性、判断依据、来源、日期和未知缺口。重要性控制细节淡化与退出日常召回的速度；“保留全部已知细节”不代表已经知道事件的全部真相，置信度也不等于重要性。

模型根据用户明确表达、个人影响与互动上下文做初评；反馈先修正具体事件，独立的多次反馈才逐渐调整同类事情的判断。偏好有版本 / 来源设计，不把助手重复提起视作重要性的证据，不因用户沉默直接下调。微调关闭也可以更新记忆偏好。

普通记忆的工作表示逐渐经历：已知细节 → 主要片段 → 事件轮廓 → 淡出日常召回。原文和归档细节仍可检索，恢复细节时应说明来自旧记录。珍藏保留细节，所有记忆都不因为被保存就每轮加载。

整理按事件和来源关联，计划逐步增加重复合并、时间线与阶段摘要；初版只做精确重复去重与有来源的提取，尚不承诺复杂事件自动合并。

## 一、记忆层次

| 层次 | 内容 | 使用方式 |
| --- | --- | --- |
| 最近上下文 | 最近消息，保留当下的连续性 | 同时受轮数与 token 预算限制 |
| 会话摘要 | 当前会话较早内容的压缩版本 | 有固定上限，增量更新，记录已覆盖消息范围 |
| 长期事实 | 用户明确表达的偏好、长期目标、已确认事实 | 按相关性检索，带来源和有效时间 |
| 事件记忆 | 决定、进展、约定等具体事件 | 结合语义、实体与时间检索 |
| 珍藏档案 | 用户希望多年保留的重要经历及原始证据 | 独立长期保存，按时间轴或回顾请求取回，不全部注入日常聊天 |
| 用户置顶 | 用户主动指定的重要信息 | 独立预算内优先保留，超限时引导用户管理 |

“长期记忆”是外部可检索的数据，不是对模型重新训练。归档原始聊天可用于用户查看和溯源，但不在每轮完整读取。

“长期保留”和“每轮注入”是两个独立策略。珍藏档案不因时间衰减自动删除，压缩仅生成便于检索和回顾的派生内容，不能覆盖它唯一的原始证据。用户仍可主动删除珍藏。

## 二、上下文预算

初始可用配置示例：给一次请求设置约 8,000 tokens 的输入上限，其中近期消息约 4,000、会话摘要约 1,000、检索记忆约 1,000，其他部分留给系统设定、置顶信息和当前问题。最终应根据模型窗口、输出预留和实测调整。

- 常规检索目标是约 3～8 条记忆；条数和总 token 数同时设限。
- 当前问题有独立长度校验；无法容纳时提示用户缩短或作为附件处理，不静默截断原意。
- 有精确 tokenizer 时按实际计数；否则使用保守估算和额外余量，不假设所有模型的中文 token 比例相同。
- 摘要达到上限时重新压缩，不无限追加。必要的稳定事实提取到可检索记忆，并保留来源。
- 预算不足时先裁剪低相关记忆与较早消息，保证当前消息、系统规则与输出预留。

固定上下文预算可以控制模型输入体积，但不保证端到端耗时固定。检索规模、embedding、模型速度和网络仍需单独测试。

## 三、召回流程

1. 从当前问题和受限的近期上下文构造查询；“那个方案”等指代需要结合近期消息解析。
2. 在当前用户与作用域内，用向量、关键词 / 实体和时间条件检索有上限的候选集。
3. 先按相关性过滤，再以重要度、有效期、显式确认和适度的时间衰减辅助排序。
4. 合并重复候选，排除过期、冲突未解决和已删除的记忆。
5. 在条数与 token 双重预算内注入；不相关时返回空集。

检索频率不能直接等同于真实重要度，否则会形成“被召回越多就越重要”的反馈循环。重要度优先依据用户明确要求、稳定性和来源可信度，其他权重通过样例评估调整，不先把某组比例当作最优值。

初期中文关键词检索必须验证分词或字符 n-gram 的实际效果；不默认 SQLite 的通用分词器能够满足中文召回需求。

回忆模式增加按年 / 月 / 事件的分层索引，允许分步查找和分页打开档案。发生时间、记录时间与用户时区分开保存；无法确定的日期标注为未知或范围，不补造精确时间。早年记忆可通过时间或事件直接找到，不以最近访问时间作为唯一入口。

## 四、写入与压缩

每轮结束后建立持久化任务，只处理尚未提取的消息和相关的已有记忆。任务有唯一键、状态、重试次数和检查点，避免重启后丢任务或重复写入。

提取结果应区分“用户明确陈述”“模型推断”和“待确认”。不把助手自己生成的猜测当作用户事实，不默认保存密码、令牌等凭据。用户可以关闭自动记忆，也可以明确要求记住某条信息。

相同事实可合并证据；表达变化不能仅凭向量相近就覆盖。新旧事实冲突时，根据明确更正、发生时间和来源处理，不确定时保留待确认状态。摘要与合并记忆保存来源消息 / 记忆关系，便于重建和删除传播。

后台压缩按阈值或空闲时段进行，不在每次发送消息前重新整理整个历史库。API 模式下后台提取也可能产生模型费用，并将相关文本发送给所选服务；这应可配置、可暂停且有用量记录。

对话可作为性格成长的有来源证据。学习开关开启后，后台在配置范围内自动整理训练样本，积累到条件满足时静默微调；相关数据有独立的版本与用途记录。记忆保存与学习开关分别控制，不以保存一条记忆为依据逐次训练或向未配置的外部服务上传数据；参见 [性格养成与训练](personality-and-learning.md)。

## 五、遗忘与删除

| 操作 | 预期行为 |
| --- | --- |
| 时间衰减 | 低价值、过时信息逐渐降低召回机会；不等于物理删除 |
| 归档 | 保留可查看记录，退出默认召回，但仍可在回忆模式中检索 |
| 珍藏 | 长期保留重要事件与证据，不因未访问自动清除；用户可明确取消或删除 |
| 标记失效 | 旧事实不作为当前事实使用，仍可用于有明确时间范围的历史查询 |
| 纠错 | 新事实生效并记录替代关系，避免两条矛盾信息同时注入 |
| 用户要求忘记 | 立即停止召回，并清理正文、向量、缓存及受影响的派生摘要；删除任务必须能查看结果 |

删除需要沿来源关系传播。只删向量不够，原文和摘要可能再次提取出同一条事实。完整删除相应事实时，还应清理或定向遮盖来源消息中的内容，并在清理完成前阻止相关任务重建；其他无关聊天可以保留。

删除记录使用不含被删正文的墓碑 / 版本号，使设备缓存和任务获知删除。恢复旧备份时必须重新应用删除记录或明确提示其范围，避免无意恢复已经忘记的信息。历史导出文件、离线备份和第三方模型供应商留存无法仅靠在线数据库操作撤回，需要单独说明和管理。

来源删除还应传播到成长证据、学习笔记、内部数据集与产物登记。已训练进模型权重的信息不能仅靠数据库删除而可靠清除，需要识别并停用受影响模型 / 适配器，切回干净版本或重新训练；遗忘状态应区分在线数据清理与训练产物处理。

## 六、建议的数据实体

- `users` / `devices`：个人身份、已配对设备、撤销状态。
- `conversations` / `messages`：原始对话及生成状态、请求幂等标识。
- `conversation_summaries`：摘要版本、覆盖范围、来源关系。
- `memories`：内容、类型、状态、重要度、有效期、来源与替代关系。
- `memory_vectors`：记忆标识、embedding 模型 / 版本 / 维度、向量。
- `memory_sources`：消息、摘要、记忆之间的来源与派生关系。
- `life_events` / `archive_items`：重要事件、珍藏状态、发生时间 / 记录时间、原始片段与可选附件引用。
- `personality_profiles` / `growth_events`：初始与当前性格版本、变化依据、来源与回滚关系。
- `learning_notes`：兴趣、探索问题、资料来源与验证状态。
- `datasets` / `dataset_samples` / `training_runs` / `model_artifacts`：样本来源、排除标记、划分、训练版本与受影响产物关系，随相关模块逐步实现。
- `jobs`：增量任务、检查点、重试和失败原因。
- `deletion_records`：不保留正文的删除范围、版本与处理状态。

所有查询都要限定用户与作用域，即使第一版只有一个用户。检索内容作为数据传入模型，不作为可以覆盖系统规则或当前用户意图的指令。

## 七、验证方式

使用可复现的对话样例测试跨会话记住、无关时不召回、新事实纠正旧事实、中文同义表达、时间变化、服务重启、删除传播与备份恢复。增加跨多年日期的回忆样本，验证未访问的珍藏不会被清除，摘要仍可追到原文，更换模型、重建向量和迁移主机后记忆仍可查。对 1,000 / 10,000 / 100,000 条记忆分别测检索耗时、输入 token、首字延迟、完整耗时和召回质量。

报告 p50 / p95，区分本地查询、embedding、模型首字与后台作业；明确测试机器、模型和网络。性能目标在首个闭环实测后确定，不先承诺一个缺乏硬件前提的毫秒数。
