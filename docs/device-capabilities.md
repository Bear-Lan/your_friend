# 日常设备能力草案

目标：yf 理解用户意图后，通过设备已有能力完成小任务，并明确显示操作状态。当前仅为设计，尚未调用任何实际闹钟、联系人或电话功能。

## 一、能力边界

| 能力 | Android | Windows | 未来常开主机 |
| --- | --- | --- | --- |
| 查时间 | 读取设备时钟与时区；无模型也能展示 | 同左 | 提供服务时间供诊断，不能冒充用户手机时间 |
| 定闹钟 | 优先调用系统闹钟；如需自管，另行实现调度与权限 | 验证系统入口或实现本地提醒；需区分睡眠 / 关机行为 | 管理约定和同步状态，不能单靠服务端定时消息保证手机闹铃 |
| 打电话 | 优先打开系统拨号界面，由用户发起呼叫 | 依赖电话处理程序、手机联动或已配置的通话服务 | 可以向已配对手机请求操作，但不能代替手机的通话链路 |
| 后续能力 | 计时器、日历、打开应用等 | 按平台逐项适配 | 只向支持该能力的设备派发 |

Windows 提醒与 Android 闹铃不是同一可靠性等级；应用需要说明实际支持的行为。更直接的自动拨号需要另行确认产品交互、权限与平台政策，第一步先做好拨号界面与明确状态。

## 二、执行链路

```mermaid
flowchart LR
    U[用户请求] --> I[意图与参数解析]
    I --> V[检查设备能力 / 时间 / 参数]
    V --> Q[展示必要澄清或确认]
    Q --> D[目标设备执行系统操作]
    D --> R[记录并展示真实回执]
```

简单的时间查询、已解析好的参数校验与本地执行可走确定性逻辑，不强制每次调用大模型。模型只提出结构化能力请求，执行器限定允许的操作，不运行任意生成的系统命令。

## 三、时间与闹钟

- 记录用户当地时区、目标设备、计划触发时刻、重复规则与任务标识。跨天、夏令时、旅行换时区时需要明确规则；“明早七点”按用户设备当前时区解析并显示具体日期。
- “七点叫我”这种存在上午 / 下午歧义的请求需要澄清。当天已经过去的时间不能静默改成明天。
- 首阶段优先使用系统闹钟入口，减少后台保活需求。系统入口若无法返回可验证结果，只报告“已打开设置闹钟界面”，不能声称“闹钟已设置成功”。
- 如后续由 yf 自主管理闹钟，需要验证系统版本、精确调度与通知权限、设备重启、取消 / 修改、勿扰与省电行为，再定义可靠性承诺。
- 一旦系统已接受本地闹钟，不应因电脑、常开主机或云端模型离线而失效；这与“手机端完整离线模型”是独立能力。

## 四、电话与联系人

“给妈妈打电话”先解析联系人。出现重名、多个号码、未授权读取联系人或目标手机不明确时，向用户澄清或交给系统联系人选择器。

调用拨号器只是打开待拨号码；“已打开拨号界面”“已提交呼叫请求”“通话已接通”是不同状态，只能依据实际可获得的系统回执显示，不能由模型推断。用户没有明确请求时，不因为旧记忆或后台任务自动发起电话。

联系人按需申请访问。用于拨号的号码可以留在设备侧，通过联系人引用匹配，避免为了简单任务把整本通讯录发送给模型或记忆库。

## 五、多设备与任务状态

每台设备声明支持的能力、权限与在线状态。服务必须明确选中执行设备，例如“这台手机”，不向所有设备广播同一操作。

任务包含唯一标识、来源消息、目标设备、有效期、参数、状态与回执。相同请求重试应去重；无法验证是否完成的操作标为待确认或未知，不盲目重试。电话等即时操作离线时提示不可用，过期后不得在设备恢复联网时突然执行。

设备间任务派发使用已配对的受保护连接。第一步以当前客户端本地执行为主；从电脑遥控手机属于后续独立功能，需要目标设备可达与可见的确认流程。

## 六、验收样例

1. 查时间返回真实设备时间与时区，模型不可用时入口仍可用。
2. 闹钟落地后关闭电脑，手机仍按已验证的系统行为响铃；界面展示的成功状态与系统结果一致。
3. 设备断网、权限被拒绝、系统入口不可用、系统只返回界面已打开时，都不伪报任务成功。
4. 电话联系人歧义会澄清；重复请求不产生重复操作；过期请求不在恢复联网后执行。
5. 另一设备不支持通话时，明确说明能力不可用或让用户选择可用手机，不把电脑的文本回复当作拨号完成。
