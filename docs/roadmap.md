# 分阶段交付草案

每个阶段都有可验收结果。当前只完成 M0 中的仓库与讨论文档，后续模块均未实现。

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| M0：架构讨论 | 陪伴定位、部署模式、技术选择、仓库结构 | 记录长期陪伴、重要回忆与日常任务目标；已确认 Android 首阶段连接电脑 / 自托管服务 |
| M1：最小服务闭环 | FastAPI、SQLite 迁移、模型适配、流式聊天、近期上下文、基础导出与一致性备份 | 配置一个可用模型后可以聊天；重启后历史仍在；取消与错误可见；备份可实际恢复 |
| M2：记忆与回忆闭环 | 长期记忆、检索、增量摘要、持久化 worker、珍藏、时间轴、纠错与遗忘 | 跨会话召回；早年重要事件可按时间查找和溯源；删除不被重新提取；上下文受预算约束 |
| M3：Windows 可用版 | Flutter 陪伴聊天、回忆页、人格与连接设置、服务生命周期、打包 | 在目标 Windows 安装运行；本地 / API 模型可配置；日常使用不需要开发命令 |
| M4：Android 可用版 | 共享客户端适配、配对、加密连接、APK | 真机安装；两端共享会话与记忆；设备访问可撤销；断网状态明确 |
| M5：日常设备能力 | 查时间、Android 系统闹钟入口、拨号入口、任务回执、Windows 平台能力验证 | 时间来自设备；权限不足不伪报成功；验证已设置闹钟在电脑离线时仍可触发；拨号与接通状态明确区分 |
| M6：长期运行完善 | 定时备份、恢复演练、用量、诊断、发布迁移、常开主机部署 | Windows 数据迁移至目标常开主机并验证；旧数据升级与恢复可重复；模型替换不丢记忆 |
| 后续扩展 | 语音、照片 / 附件、知识库、更多工具、可配置主动陪伴、手机完整离线能力 | 分别评估后建立独立验收标准，不计入首阶段承诺 |

M3 / M4 的界面可以在服务接口稳定后交错开发。两个端都属于目标产品，先完成 Windows 是为便于在本机验证模型、记忆和服务打包。

基础备份与来源追踪进入 M1 / M2，不能推迟到多年使用之后。M6 完善的是自动化与跨主机部署。设备侧查时间等简单能力可提前穿插开发，但不能挤掉陪伴和记忆闭环。

## 首次开发迭代建议

先实现服务端核心链路与简单调试入口，完成一组可重复的对话与记忆测试，再接正式 Flutter UI。没有 GPU 或未下载本地模型时，可用用户选择的 API 验证同一套流程；测试不依赖把私密对话上传到公共环境。

验收场景：用户说“以后叫我小熊，我正在做 yf”，新建会话后询问项目时可取回相关记忆；询问无关问题时不强行注入；将项目名更正后只按新事实回答；用户要求忘记昵称后，跨会话与服务重启都不会再次召回昵称。

多年回忆场景：导入带明确历史日期的旅行记录并珍藏，模拟多年未访问后仍可按事件找到原文；迁移主机、更换聊天模型和重建向量后重复验证。通过历史样本验证可迁移性与逻辑行为，不把模拟通过等同于已经保证多年运行。

## 发布准备

Windows 安装形式和最低系统版本在框架确认后确定；Android 最低版本根据 Flutter 插件与目标设备确定。确认 Flutter、Android SDK、受支持的 JDK 和 Windows 原生构建工具链后再建立实际构建流程，不能仅以项目目录存在作为可发布的依据。

首个版本不要求托管云账号体系、应用商店上架、自动更新或端到端离线同步。这些需求如要纳入首发，应重新评估阶段范围。
