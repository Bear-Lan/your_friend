# 分阶段交付草案

每个阶段都有可验收结果。当前只完成 M0 中的仓库与讨论文档，后续模块均未实现。

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| M0：架构讨论 | 产品范围、部署模式、技术选择、仓库结构 | 关键决策有记录；已确认 Android 首阶段连接电脑 / 自托管服务 |
| M1：最小服务闭环 | FastAPI、SQLite 迁移、模型适配、流式聊天、近期上下文 | 配置一个可用模型后可以聊天；刷新 / 重启后历史仍在；取消与错误可见 |
| M2：记忆闭环 | 长期记忆、检索、增量摘要、持久化 worker、纠错与遗忘 | 新会话可召回明确事实；无关问题不注入；删除不会被后台重新生成；上下文受预算约束 |
| M3：Windows 可用版 | Flutter 客户端、记忆页、设置、服务生命周期、打包 | 在目标 Windows 机器安装运行；本地 / API 模型可配置；无需开发命令完成日常聊天 |
| M4：Android 可用版 | 共享客户端适配、配对、加密连接、APK | 真机安装；连接同一服务后两端共享会话与记忆；设备访问可撤销；断网状态明确 |
| M5：日常使用完善 | 备份 / 恢复 / 导出、用量、错误诊断、发布与迁移 | 升级和恢复经过实际验证；密钥不进入日志 / 仓库；运行配置有文档 |
| 后续扩展 | 语音、附件、知识库、工具调用、手机完整离线能力 | 分别评估后建立独立验收标准，不计入首阶段承诺 |

M3 / M4 的界面可以在服务接口稳定后交错开发。两个端都属于目标产品，先完成 Windows 是为便于在本机验证模型、记忆和服务打包。

## 首次开发迭代建议

先实现服务端核心链路与简单调试入口，完成一组可重复的对话与记忆测试，再接正式 Flutter UI。没有 GPU 或未下载本地模型时，可用用户选择的 API 验证同一套流程；测试不依赖把私密对话上传到公共环境。

验收场景：用户说“以后叫我小熊，我正在做 yf”，新建会话后询问项目时可取回相关记忆；询问无关问题时不强行注入；将项目名更正后只按新事实回答；用户要求忘记昵称后，跨会话与服务重启都不会再次召回昵称。

## 发布准备

Windows 安装形式和最低系统版本在框架确认后确定；Android 最低版本根据 Flutter 插件与目标设备确定。确认 Flutter、Android SDK、受支持的 JDK 和 Windows 原生构建工具链后再建立实际构建流程，不能仅以项目目录存在作为可发布的依据。

首个版本不要求托管云账号体系、应用商店上架、自动更新或端到端离线同步。这些需求如要纳入首发，应重新评估阶段范围。
