# 分阶段交付草案

每个阶段都有可验收结果。目前已开始实现 M1 与 M2 的本机验证闭环，具体可运行能力见 [运行文档](running.md)；不将部分实现标为整个阶段完成。

已实现：本地服务、流式聊天适配、历史保存、初始交流倾向、持久化整理任务、来源与重要性、细节淡化、用户反馈与有限主题偏好、手动珍藏、删除预览、档案检索、备份恢复和网页验证入口。

进一步已实现：可迁移的本地特征档案，包含六项表达倾向、重要性判断侧重、行为说明与风格样例，保存 / 回退 / 导出 / 备份均保留版本，模型请求按预算携带档案。数据库升级前自动备份。

界面已改为一个连续聊天页面、程序化立体虚拟伙伴、回忆与设置抽屉。固定聊天入口在刷新 / 重启后恢复同一历史；旧记录仍可检索查看。3D 资源本地打包，具有基本动作与 WebGL 降级；尚不包含真人模型导入、口型同步或语音。

待继续验证 / 实现：真实模型质量、语义向量检索、滚动会话摘要、复杂事件合并、自动性格成长、Flutter 客户端、移动配对、系统任务和静默微调。没有模型配置时不生成替代回复。

空间管理方向已确认：记忆整理逐步压缩低重要度细节、合并重复并清理冗余派生内容；多年运行阶段补充容量统计、归档与实际空间回收。整理不撤销已形成的性格、偏好和训练成果，不要求模型反学习；原始聊天仍默认长期保留。当前召回淡化与关联删除不等于已经实现自动空间整理。

M3 / M4 的界面可以在服务接口稳定后交错开发。两个端都属于目标产品，先完成 Windows 是为便于在本机验证模型、记忆和服务打包。

基础备份与来源追踪进入 M1 / M2，不能推迟到多年使用之后。M6 完善的是自动化与跨主机部署。设备侧查时间等简单能力可提前穿插开发，但不能挤掉陪伴和记忆闭环。

训练样本的来源标识、用途排除与学习设置在数据层初期预留，基础数据集导出可以提前。M2 的性格养成也遵循学习开关；M7 完成真正的后台权重微调、评估与自动启用。模型和设备能力不足时明确展示限制，不将档案变化当作训练完成；不承诺所有 API 都可微调。

## 首次开发迭代建议

先实现服务端核心链路与简单调试入口，完成一组可重复的对话与记忆测试，再接正式 Flutter UI。没有 GPU 或未下载本地模型时，可用用户选择的 API 验证同一套流程；测试不依赖把私密对话上传到公共环境。

验收场景：用户说“以后叫我小熊，我正在做 yf”，刷新或重启后仍回到同一聊天；超过近期上下文预算后询问项目时可取回相关记忆；询问无关问题时不强行注入；将项目名更正后只按新事实回答；用户要求忘记昵称后，服务重启都不会再次从外部记忆召回昵称。

多年回忆场景：导入带明确历史日期的旅行记录并珍藏，模拟多年未访问后仍可按事件找到原文；迁移主机、更换聊天模型和重建向量后重复验证。通过历史样本验证可迁移性与逻辑行为，不把模拟通过等同于已经保证多年运行。

## 发布准备

Windows 安装形式和最低系统版本在框架确认后确定；Android 最低版本根据 Flutter 插件与目标设备确定。确认 Flutter、Android SDK、受支持的 JDK 和 Windows 原生构建工具链后再建立实际构建流程，不能仅以项目目录存在作为可发布的依据。

首个版本不要求托管云账号体系、应用商店上架、自动更新或端到端离线同步。这些需求如要纳入首发，应重新评估阶段范围。
